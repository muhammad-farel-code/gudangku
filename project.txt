3. FITUR + BUSINESS RULES
================================================================================

NAMA APLIKASI : GudangKu
TAGLINE       : Sistem manajemen inventaris gudang: stok masuk, stok keluar,
                opname, dan laporan, dengan kontrol akses berbasis peran.
DESKRIPSI     : Aplikasi web server-side (Laravel, MVC, MySQL) untuk mencatat
                master barang, kategori, pemasok, serta seluruh pergerakan
                stok (masuk, keluar, penyesuaian) dengan jejak audit dan
                dashboard ringkasan. Akses dibatasi 3 peran: Admin, Manager,
                Staff.

--- PRIORITAS ---
P0 = wajib (menjamin nilai).  P1 = nilai tambah.  P2 = hanya kalau waktu sisa.

[A] AUTENTIKASI & SESI (P0)
  A1. Registrasi (nama, email, password + konfirmasi). Role otomatis `staff`
      (role TIDAK PERNAH diambil dari input).
  A2. Login (email + password), pesan error generik, regenerate session,
      throttle 5x/menit per email+IP.
  A3. Logout (POST, invalidate session, regenerate CSRF token).
  A4. User nonaktif (`is_active=false`) tidak bisa login / langsung ditendang.
  A5. Profil: ubah nama, ubah password (butuh password lama).   (P1)

[B] DASHBOARD (P0)
  B1. Kartu ringkasan: total produk, total unit stok, nilai persediaan
      (SUM stock x purchase_price), jumlah produk stok menipis.
  B2. Tabel "Stok Menipis" (stock <= min_stock).
  B3. Grafik Chart.js: stok masuk vs keluar 7/14 hari terakhir.      (P1)
  B4. 5-10 transaksi terbaru.
  Isi dashboard menyesuaikan role (staff tidak melihat nilai persediaan).

[C] MASTER DATA - CRUD PENUH (P0)
  C1. Kategori: index (search+paging), create, show/edit, update, delete.
  C2. Pemasok (supplier): CRUD penuh.
  C3. Produk: CRUD penuh + search (nama/SKU) + filter kategori + filter
      "stok menipis" + pagination + badge status stok. Stok awal lewat
      `initial_stock` yang otomatis membuat transaksi "Stok awal".
  C4. Manajemen user (admin): CRUD, ubah role, aktif/nonaktif, reset password.

[D] TRANSAKSI STOK (P0)
  D1. Stok Masuk (IN): pilih produk, qty, pemasok, tanggal, no. referensi
      (auto), catatan. Stok produk bertambah.
  D2. Stok Keluar (OUT): pilih produk, qty, penerima/tujuan, tanggal, catatan.
      Ditolak jika qty > stok tersedia.
  D3. Penyesuaian / Stock Opname (ADJUSTMENT): input stok fisik hasil hitung,
      sistem menghitung selisih. Hanya manager/admin.
  D4. Riwayat transaksi: filter tanggal, tipe, produk; pagination; detail.
  D5. Transaksi bersifat IMMUTABLE (ledger): tidak ada edit/hapus. Koreksi
      dilakukan lewat transaksi penyesuaian. (Alasan desain untuk esai.)

[E] LAPORAN (P1)
  E1. Laporan stok saat ini (filter kategori) + export CSV + tampilan cetak.
  E2. Laporan transaksi per periode + export CSV.
  E3. Export CSV aman dari CSV/Formula injection (awali sel yang berawalan
      = + - @ dengan tanda petik tunggal).

[F] AUDIT & KEAMANAN TAMBAHAN (P1)
  F1. Activity log: login, logout, create/update/delete master, transaksi
      stok, perubahan role. Halaman log (admin).
  F2. Security headers middleware.
  F3. Halaman error kustom: 403, 404, 419 (sesi kedaluwarsa), 500.

[G] OPSIONAL (P2)
  G1. Upload foto produk (hati-hati: filesystem Railway ephemeral; lewati
      kalau tidak ada waktu).
  G2. Dark mode, export PDF, notifikasi email stok menipis. (Skip saja.)

--- BUSINESS RULES (harus konsisten di kode, test, dan esai) ---
  BR1  Stok tidak boleh negatif (validasi + pengecekan di service + CHECK
       logika di transaksi DB).
  BR2  Stok produk HANYA berubah lewat StockService (tidak ada edit stok
       langsung di form produk).
  BR3  Setiap perubahan stok atomik: DB::transaction + lockForUpdate pada
       baris produk (mencegah race condition / oversell).
  BR4  SKU unik (MySQL collation case-insensitive).
  BR5  Kategori tidak bisa dihapus bila masih punya produk (FK restrict ->
       tampilkan pesan ramah, bukan error 500).
  BR6  Produk yang sudah punya transaksi tidak bisa dihapus (restrict).
       Jika perlu, set `is_active=false` (produk nonaktif tidak muncul di
       dropdown transaksi).
  BR7  Hapus pemasok -> supplier_id di produk & transaksi jadi NULL (histori
       tetap aman).
  BR8  Registrasi selalu role `staff`. Hanya admin yang bisa ubah role.
  BR9  Admin tidak bisa menghapus/menonaktifkan/menurunkan role dirinya
       sendiri, dan minimal 1 admin aktif harus tetap ada.
  BR10 Harga jual >= harga beli.
  BR11 Stok menipis = stock <= min_stock.
  BR12 Nomor referensi transaksi unik, format: IN-YYYYMMDD-0001 /
       OUT-... / ADJ-... (urutan harian).

(*) Staff tidak melihat kartu "Nilai Persediaan" (informasi finansial).

IMPLEMENTASI (dua lapis, ini poin nilai "Role based access policy"):
  Lapis 1 - Middleware `role:admin,manager` (EnsureUserHasRole) di group
            route -> kasar, per-halaman. Gagal -> 403.
  Lapis 2 - Policy (UserPolicy, ProductPolicy, dll.) di controller via
            $this->authorize() -> halus, per-record/aturan (mis. admin tidak
            boleh hapus dirinya sendiri).
  Lapis 3 - Blade @can / @if(auth()->user()->hasRole(...)) hanya untuk
            menyembunyikan tombol/menu. Ini kosmetik; server tetap menolak.
  Catatan: Laravel 11+ tidak punya app/Http/Kernel.php. Alias middleware
  didaftarkan di bootstrap/app.php. Policy ditemukan otomatis lewat
  konvensi nama (App\Models\Product -> App\Policies\ProductPolicy).

--- 5.2 DETAIL TABEL ---

users (modifikasi migration bawaan Laravel sebelum migrate pertama)
  id, name(100), email(150, unique), email_verified_at(nullable), password,
  role ENUM('admin','manager','staff') DEFAULT 'staff' [index],
  is_active BOOLEAN DEFAULT 1, remember_token, timestamps.

categories
  id, name(100, unique), description(text, nullable), timestamps.

suppliers
  id, name(150), contact_person(100,null), phone(30,null), email(150,null),

products
  id, category_id (FK categories, RESTRICT ON DELETE),
  supplier_id (FK suppliers, nullable, SET NULL ON DELETE),

  purchase_price DECIMAL(15,2) default 0, selling_price DECIMAL(15,2) default 0,

stock_transactions
  id, reference_no(30, unique),
  product_id (FK products, RESTRICT), user_id (FK users, RESTRICT),
  supplier_id (FK suppliers, nullable, SET NULL),
  type ENUM('in','out','adjustment') [index],
  quantity UNSIGNED INT (besar perubahan, selalu positif),
  stock_before UNSIGNED INT, stock_after UNSIGNED INT,

================================================================================
6. ARSITEKTUR APLIKASI
================================================================================

--- 6.1 Pola ---
MVC klasik Laravel + 3 lapisan pendukung agar controller tetap tipis:

  Model        : Eloquent (relasi, casts, fillable, scope, accessor).
  View         : Blade (layout, partials, komponen sederhana).
  Controller   : tipis; menerima Request, memanggil FormRequest/Service/Model,
                 mengembalikan view/redirect.
  FormRequest  : validasi + sanitasi + otorisasi input.
  Service      : StockService (logika bisnis stok, transaksi DB), 
                 ActivityLogger (audit).
  Policy       : otorisasi per-aksi/record.
  Middleware   : EnsureUserHasRole, EnsureUserIsActive, SecurityHeaders.
  Exception    : InsufficientStockException (domain error -> flash error).

--- 6.2 Request lifecycle (untuk diagram alur & esai) ---
Flowchart (Mermaid):

flowchart TD
    A[Browser: HTTP Request] --> B[public/index.php]
    B --> C[bootstrap/app.php: boot framework]
    C --> D[Global middleware: TrustProxies, SecurityHeaders]

8. KEAMANAN (CPMK4 - bobot 15% + esai)
================================================================================

Checklist implementasi. Tiap poin = bukti di kode + screenshot + bahan esai.

[8.1] CSRF
  - Semua <form> method POST/PUT/PATCH/DELETE memuat @csrf (+ @method).
  - Middleware VerifyCsrfToken aktif (bawaan group `web`). Jangan pernah
    menambahkan pengecualian di `validateCsrfTokens(except: ...)`.
  - Logout lewat POST. Halaman 419 kustom untuk sesi/token kedaluwarsa.
  - Demo: hapus token via DevTools lalu submit -> muncul 419.
  - Catatan: saat menjalankan test, CSRF dimatikan otomatis oleh framework;
    verifikasi CSRF dilakukan manual + dijelaskan di esai.

[8.2] XSS
  - Output Blade pakai {{ $var }} (auto htmlspecialchars). DILARANG {!! !!}
    untuk data pengguna.
  - Sanitasi input: di FormRequest::prepareForValidation() jalankan
    trim() + strip_tags() untuk field teks (name, description, notes,
    recipient, address, dll.).
  - Dalam atribut HTML/JS: untuk data ke JavaScript (Chart.js) gunakan
    @json($data) atau Js::from($data), bukan echo mentah.
  - Header X-Content-Type-Options: nosniff; (opsional) Content-Security-Policy
    report-only. Karena memakai CDN, jika CSP diaktifkan whitelist host CDN.
  - Test: simpan produk bernama `<script>alert(1)</script>` -> halaman
    menampilkan teks literal, tidak mengeksekusi.

[8.3] SQL INJECTION
  - Semua query lewat Eloquent / Query Builder (PDO prepared statements,
    parameter binding).
  - Bila butuh raw (SUM/GROUP BY), pakai selectRaw('... ?', [$binding]) atau
    ekspresi statis tanpa input pengguna. DILARANG menyambung string input
    ke SQL. Kolom sorting dari user harus lewat whitelist.
  - LIKE search: where('name', 'like', "%{$q}%") tetap aman (binding), tapi
    escape karakter % dan _ jika mau presisi.
  - Demo: input `' OR 1=1 --` di kolom search/login -> tidak berpengaruh.

[8.4] AUTENTIKASI & PASSWORD
  - Hash::make / cast 'hashed' (bcrypt, BCRYPT_ROUNDS=12). Tidak ada password
    plaintext, tidak ada password di log.
  - Password::defaults(): min 8, mixedCase, numbers (di AppServiceProvider).
  - Login: Auth::attempt(['email'=>..,'password'=>..,'is_active'=>1]).
    Pesan gagal generik: "Email atau password salah." (anti user enumeration).
  - Throttle: RateLimiter::for('login') 5/menit by email+IP.
  - Mass assignment: $fillable eksplisit; `role` & `is_active` TIDAK ada di
    $fillable untuk jalur registrasi publik (set manual di controller admin).

[8.5] SESSION
  - SESSION_DRIVER=database, lifetime 120 menit, http_only=true,
    same_site=lax, secure cookie=true di production (HTTPS).
  - Login sukses: $request->session()->regenerate()  (cegah session fixation).
  - Logout: Auth::logout(); session()->invalidate(); session()->regenerateToken().
  - Middleware EnsureUserIsActive: jika user dinonaktifkan saat sesi aktif ->
    logout paksa.
  - Ubah password -> regenerate session (opsional Auth::logoutOtherDevices).

[8.6] OTORISASI (RBAC)
  - Middleware role + Policy + @can (lihat Bagian 4). Selalu validasi di
    server. Uji manual: login staff lalu buka URL admin langsung -> 403.
  - IDOR: pakai route model binding + policy; tidak pernah percaya id
    dari form hidden tanpa validasi `exists`.

[8.7] VALIDASI INPUT SERVER-SIDE
  - Semua input lewat FormRequest (aturan di Bagian 9). Tidak ada
    $request->all() langsung ke create(); pakai $request->validated().

[8.8] HARDENING LAIN
  - APP_DEBUG=false & APP_ENV=production di live (jangan bocorkan stack trace).
  - .env tidak di-commit. Hanya .env.example.
  - SecurityHeaders middleware: X-Frame-Options: SAMEORIGIN,
    X-Content-Type-Options: nosniff, Referrer-Policy:
    strict-origin-when-cross-origin, Permissions-Policy (matikan kamera,
    mikrofon, geolokasi), Strict-Transport-Security (hanya production).
  - trustProxies(at: '*') di Railway agar URL https & cookie secure benar.
  - Export CSV: netralkan formula injection.
  - Log error ke stderr di production; jangan tampilkan detail ke user.

TABEL RINGKAS UNTUK PDF/ESAI:
  Ancaman          | Mitigasi di GudangKu                      | Lokasi kode
  CSRF             | @csrf + VerifyCsrfToken                   | semua form
  XSS              | {{ }} escape + strip_tags di FormRequest  | views, Requests
  SQL Injection    | Eloquent/Query Builder binding            | controllers/services
  Brute force      | throttle login 5/menit                    | AppServiceProvider
  Session fixation | regenerate saat login                     | AuthController

# Coding Standards GudangKu

## Arsitektur
- MVC + FormRequest + Service + Policy. Controller TIPIS (maks ~25 baris/method).
- Logika stok HANYA di App\Services\StockService. Controller tidak mengubah

- Blade layout + partials. Semua output pakai {{ }}. JANGAN {!! !!} untuk

---------- FILE 3: .agents/rules/02-security.md ----------
# Security Rules GudangKu (NON-NEGOTIABLE)

1. CSRF: semua form non-GET punya @csrf. Jangan menambah pengecualian CSRF.
2. XSS: escape default Blade; strip_tags + trim di prepareForValidation()
   untuk field teks bebas. Tidak ada {!! !!} untuk input user.
3. SQL Injection: hanya Eloquent/Query Builder dengan binding. Raw SQL hanya
   dengan binding atau ekspresi statis; sorting dinamis lewat whitelist.
4. Auth manual: Auth::attempt dengan kondisi is_active=1; pesan gagal generik;
   session()->regenerate() saat login; invalidate() + regenerateToken() saat
   logout (logout via POST).
5. Password: Hash (cast 'hashed'), Password::defaults() min 8 + mixedCase +
   numbers. Jangan pernah log/echo password.
6. Mass assignment: $fillable eksplisit. `role` & `is_active` TIDAK boleh
   masuk dari registrasi publik. Registrasi publik = role staff.
7. RBAC: terapkan di server (middleware + Policy). Menyembunyikan tombol di
   Blade BUKAN keamanan. Admin tidak boleh hapus/nonaktifkan/ubah role diri
   sendiri; minimal 1 admin aktif.
8. Rate limit login: 5 percobaan/menit per email+IP.
9. Header keamanan via middleware SecurityHeaders.

       stock_before/after di transaksi untuk audit & kinerja.
Q5. Kenapa stok disimpan di products dan juga ada tabel transaksi?
    -> Baca stok cepat (tanpa SUM tiap kali) + ledger untuk jejak audit;
       konsistensi dijaga transaksi DB + lock.
Q6. Eloquent vs Query Builder, kapan dipakai?
    -> Eloquent untuk CRUD/relasi/eager loading; Query Builder untuk agregasi
       laporan/dashboard (groupBy, sum) yang lebih ringan.
Q7. Apa itu migration & seeder, kenapa penting?
    -> Skema sebagai kode (versi, reproducible, tim); seeder untuk data demo.
Q8. Apa itu N+1 dan bagaimana mencegahnya?
    -> with('category','supplier') pada index produk.
Q9. Jelaskan foreign key & aksi onDelete yang kamu pilih.
    -> restrict pada kategori/produk (jaga integritas), set null pada pemasok
       (histori tetap).

--- Kelompok 2: Backend, error, sekuriti ---
Q10. Bagaimana mencegah stok negatif dan race condition?
    -> DB::transaction + lockForUpdate (row lock), cek stok di service,
       exception domain, rollback otomatis.
Q11. Bagaimana validasi dilakukan dan kenapa server-side?
    -> FormRequest; client-side bisa dibypass; validated() hanya data valid.
Q12. Bagaimana CSRF dicegah? Apa yang terjadi tanpa token?
    -> Token per sesi di @csrf, dicek VerifyCsrfToken; tanpa token -> 419.
Q13. Bagaimana XSS dicegah?
    -> Escape output Blade {{ }}, strip_tags saat input, tanpa {!! !!},
       @json untuk JS, header nosniff.
Q14. SQL Injection? 
    -> PDO prepared statements lewat Eloquent/QB; tidak ada concat input;
       whitelist sorting.
Q15. Bagaimana autentikasi & session bekerja?
    -> Auth::attempt (cek hash bcrypt), session ID di cookie httpOnly, data
       sesi di tabel sessions, regenerate saat login (anti fixation),
       invalidate saat logout.
Q16. Bagaimana RBAC diterapkan? Apa bedanya middleware dan policy?
    -> Middleware: gerbang per-route berdasar role; Policy: aturan per-aksi
       & per-record (mis. admin tak boleh hapus diri sendiri).
Q17. Bagaimana error ditangani?
    -> Validasi (redirect+pesan), exception domain, FK constraint ramah,
       log error, halaman error kustom, APP_DEBUG=false di production.
Q18. Kenapa registrasi selalu role staff?
    -> Cegah privilege escalation/mass assignment; admin yang mengubah role.
Q19. Kenapa transaksi stok tidak bisa diedit/dihapus?
    -> Integritas audit (ledger); koreksi via adjustment yang tercatat.
Q20. Bagaimana kamu memastikan kode orisinal & kamu paham?
    -> Commit history bertahap, AI dipakai sebagai asisten dengan rules,
       setiap fase direview & dijelaskan ulang, tes ditulis & dijalankan.
       (Jawab JUJUR soal penggunaan AI; soal mengizinkan asal paham.)

--- Kelompok 3: Deployment, env, troubleshooting ---
Q21. Langkah deployment? -> Bagian 15.
Q22. Fungsi .env & kenapa tidak di-commit? 
    -> Konfigurasi per-lingkungan + secret; .env.example sebagai template.
Q23. APP_KEY untuk apa? -> Enkripsi cookie/sesi terenkripsi; tanpa itu error.
Q24. Perbedaan lokal vs production? 
    -> APP_DEBUG false, cookie secure, log stderr, DB managed, HTTPS via proxy,
       cache config/route/view.
Q25. Masalah yang kamu temui saat deploy & solusinya? 
    -> Siapkan 2-3 cerita NYATA dari pengalamanmu (catat selama mengerjakan!).
       Contoh: trustProxies, DB env reference, seeder duplikat, migrate lupa.
Q26. Bagaimana menjaga data tidak hilang saat redeploy? -> DB terpisah (MySQL
     service), tidak simpan state di filesystem container.

TIPS: buat file `docs/catatan-troubleshooting.md` sejak sekarang dan catat
SETIAP error yang kamu temui beserta solusinya. Itu bahan esai paling otentik.

22. TROUBLESHOOTING UMUM
================================================================================
Lokal
  - "could not find driver" -> aktifkan ekstensi pdo_mysql di php.ini.
  - "Access denied for user 'root'" -> sesuaikan DB_USERNAME/DB_PASSWORD.
  - "Base table or view not found: sessions" -> php artisan migrate.
  - "Class not found" setelah buat file -> composer dump-autoload.
  - Perubahan .env tak berlaku -> php artisan config:clear.
  - Route tidak ketemu -> php artisan route:list, route:clear.
  - View lama muncul -> php artisan view:clear.
  - 419 saat submit -> lupa @csrf atau sesi habis.
  - Tes gagal karena DB -> pastikan gudangku_test ada & phpunit.xml pakai mysql.
  - MySQL strict mode error -> cek tipe data/panjang kolom vs input.
AI / Antigravity
  - AI memakai sintaks Laravel lama (Kernel.php, $routeMiddleware) -> ingatkan
    versi Laravel di composer.json & rules; minta cek dokumentasi.
  - AI memasang package/starter kit -> tolak, revert, rujuk rules file 00.
  - AI mengubah banyak file di luar fase -> git diff, revert yang di luar scope.
  - Kode terlalu rumit untuk kamu jelaskan -> minta disederhanakan sebelum commit.
  - Konteks membengkak/halusinasi -> buka chat baru per fase, tempel ringkasan
    keputusan + path file relevan.
